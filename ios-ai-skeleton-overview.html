iOS AI-Optimized
Skeleton — the guide

A template for starting a new iOS project that an AI coding agent can work in without re-deriving your conventions every session. Eleven questions at setup produce a compiling app, a rendered rulebook the agent auto-loads, and deterministic scaffolding for everything after.

Written for iOS developers moving to agent-assisted work: it assumes Xcode, Swift and SPM, and explains only what's specific to this template. Covers greenfield use — /start can also adopt an existing app, but that path is out of scope here.

01

Why this exists

You already know how to build the app. What you don't have is a way to make an AI assistant build it the same way twice. It has no memory between sessions, so unless your conventions are written where it loads them automatically, screen forty is built however that morning's conversation went — a different folder shape, a different navigation call, a view model wired straight to URLSession.

This kit records those decisions once, at setup, into files the assistant reads at the start of every session, and generates code that follows them. Scaffolding and a rulebook, not a framework.

  • A compiling app on the first run — one screen with loading, error and empty states, a network layer, theme tokens, per-module localization, and a test that has already passed. Answer None to networking and one thing is left for you: that screen's local-store read and its test ship red on purpose.
  • Meta-files the assistant loads by itself — see 03.
  • Nine commands for the work you repeat: a screen, an asset, a permission, a token, a locale, a module.
  • Commit-time guards for hardcoded colours, string-key drift, lint and commit format.
Before anything else This repository is the template, not an app — no .xcodeproj, no chosen pattern, nothing app-shaped until you run /start.

Where the defaults come from

Not taste — one long-lived production workspace: two apps on a shared framework spine, ~20 feature flows each, 18 localizations, several years of history.

  • observedShared code vends base view controllers and flows each app configures, never finished screens. App-specific behaviour arrives injected — never if app == .x inside a shared module.
  • observed18 locales maintained per module — a bundle-resolution consequence, not a preference.
  • recommendedDon't abstract on speculation. The threshold for a protocol is a second real conformance — a test fake counts, a future backend doesn't.

Fill in Secrets.xcconfig before the first build

/start leaves two files at the repo root: Secrets.xcconfig.example, committed, which records which keys exist, and Secrets.xcconfig, which is gitignored and holds the real values. Set API_BASE_URL there — not in Swift.

Secrets.xcconfiggitignored
// `//` starts a comment here, so a URL's scheme needs the $() escape
API_BASE_URL = https:/$()/api.staging.example.com

The value reaches the app as the target's Info.plist key APIBaseURL, which the composition root reads and injects into RequestBuilder. Leave it empty and the app crashes at launch with a message telling you which file to fix — deliberate, because a fallback URL is a staging build silently talking to the wrong server. Every fresh clone repeats this step.

That check tests for a scheme and a host, not merely that the string parsed — which is what catches the mistake the $() above exists for. Quoting is not an alternative: xcconfig has no string literals and no escape character, so "https://host" truncates exactly like the bare form. $() works by expanding to nothing after the comment is stripped, so the // is never adjacent while anything is looking for it. Scripts/check_secrets.sh applies the same rules at commit time, and docs/CODING_STANDARDS.md has the full mechanism with a table of what every candidate form resolves to.

Answer None to the networking question and this step doesn't exist: an offline app renders no RequestBuilder, no APIBaseURL key and no reader, so there's nothing to fill in and nothing to crash about. The rule is don't render the reader, never make the read tolerant — softening the check to suit offline apps would trade a correct crash for a networked build quietly pointing at the wrong server.

The project file is generated Don't add or move files in Xcode's navigator — the next regenerate overwrites it. Edit project.yml, or use the commands.

Do's and don'ts

Everything /start writes is downstream of your eleven answers, so the session that produces them is the one worth getting right.

Do

Answer the eleven as a set

They're validated as a set, not one at a time. "Use the recommended defaults" is a complete answer; a guessed one propagates into every command that reads the config afterwards.

Do

Re-run /start when something's missing

It's idempotent: it recreates what's absent and refuses structural changes as a re-run side effect. Reaching for it a second time is safe, and cheaper than reconstructing a file by hand.

Don't

Copy the template files in by hand

/start walks them file-by-file and never overwrites something already there, which is exactly what makes that re-run safe. A manual cp -r loses both.

Don't

Point /start at a hand-maintained Xcode project

It never regenerates or overwrites one. Adopting an existing codebase is a different path from scaffolding a greenfield, and it will tell you so rather than scaffolding over the top.

03

The knowledge base

The assistant starts every session knowing nothing about your project. These files answer, in advance, what it would otherwise guess. CLAUDE.md loads automatically and points at the rest.

On a greenfield project it arrives three ways

  • Copied in finished — the rules independent of your answers: theming, UI, permissions, coding standards, git conventions.
  • Rendered by /start — the templates ship describing every pattern and tier; the render deletes the ones you didn't choose, so your docs describe one architecture, not five. No placeholder survives it.
  • Written by you — docs/product/. The template knows how an app here is built and nothing about what it's for; requirements arrive later, keep changing, and are read fresh each time rather than digested into CLAUDE.md.
  • Grown as you work — seeded at setup, then appended to by the commands that change what they describe.

The Swift-level calls the rulebook makes for you

None of these follow from your eleven answers, and all four are questions an assistant will otherwise answer by habit — badly, in the same four ways. They're written down so it doesn't have to guess, each one anchored in code the template actually ships.

QuestionThe call, and what it's anchored in
Where does this data go? UserDefaults for small non-sensitive state and preferences · the persistence stack you chose for domain records · Keychain for tokens and credentials, the only encrypted store and the only one kept out of unencrypted backups. The hard line: never a credential in UserDefaults or the local database. UserDefaults itself goes behind a narrow protocol, not reached for as a global
GCD or async/await? async/await, and the generated code already is: every service, repository and store is async throws, Debouncer is an actor, UI-owning types are @MainActor, and no template contains a single DispatchQueue. GCD only where an SDK forces it — wrapped once in a continuation at the boundary. An actor for shared mutable state rather than a serial queue; @MainActor rather than DispatchQueue.main.async; never a semaphore blocking on async work
When is [weak self] needed? Keyed to ownership direction, not sprinkled. An escaping closure stored on a long-lived object needs it — the generated retry handler is the shape; a non-escaping one doesn't, and adding it there is noise. A back-reference up the graph is always weak, which is why VIP's presenter holds its display layer weakly. Prefer weak over unowned: unowned is a crash where weak is a no-op
struct or class? struct by default; class for identity (a coordinator, a view model), a framework requirement (UIViewController, @Model, or needing to be the target of a weak reference), or @Observable view state. Models, RequestBuilder and the API client are structs because none of those apply. Mark classes final unless something subclasses them, and remember a struct holding a mutable reference is not a value type
Stale is worse than absent An architecture doc describing a pattern you've moved away from doesn't fail loudly — it steers the assistant wrong for months. The commands append rather than leaving it to discipline, and /status reports drift between what's recorded and what's on disk.

Do's and don'ts

These files exist so a session doesn't start by re-establishing what the last one already knew. Using them well is mostly a matter of where you put a sentence.

Do

Write the answer down, not just into the chat

The assistant has no memory between sessions. A constraint you explain in conversation is gone tomorrow; the same sentence in docs/product/ or PROJECT_MAP.md loads every time, unprompted.

Do

Point at the file rather than pasting its contents

"Read docs/product/api-contracts.md before building this service" costs a fraction of pasting the document, and stays correct after the document changes.

Do

Let the commands do the appending

PROJECT_MAP.md, PERMISSIONS.md and TODO.md are seeded at setup and then written to by the commands that change what they describe — grown as you work, rather than maintained by discipline.

Don't

Re-state your stack, tier and pattern each session

CLAUDE.md is loaded automatically before your first message is read. Restating it spends context on what's already there, and a restatement that drifts from the file is worse than silence.

Don't

Summarize docs/product/ into CLAUDE.md

Requirements keep changing, and a digest goes stale without failing. CLAUDE.md points at them and never summarizes them; /new-feature re-reads the relevant one per invocation.

Don't

Keep the patterns you didn't choose "for reference"

The render deletes them on purpose, so your docs describe one architecture rather than five. A pattern left in the file is a pattern the assistant may decide is on the menu.

04

Project topology

The layers are identical at all three tiers — only the packaging changes, which is what keeps migration tractable. What differs is whether the compiler can enforce a boundary.

T1T2 defaultT3
Shapeone .xcodeproj, one app target+ local Swift packages under Packages/.xcworkspace over N projects: app + dynamic framework targets
Swift modulesone — all internalone per package; crossing needs public plus an explicit public initone per framework, each with a shared scheme, independently buildable
Spec filesone project.yml+ a Package.swift per packageone per project, plus a generated contents.xcworkspacedata
Lock filePackage.resolved inside App.xcodeproj/…/swiftpm/moves to xcshareddata/swiftpm/
Good forprototypes, <10 screensone shipping app, any sizetwo apps sharing a spine, or a shipped framework

Dependencies point one way — app targets → shared modules → leaf modules; never framework to app or app to app. A shared module needing app-specific behaviour takes it as a protocol injected at the composition root. /add-module refuses to create a cycle.

Cheap to add, expensive to retrofit Adding a package or project is a spec edit plus a regenerate — never pbxproj surgery. Extracting shared code from an app target that never had boundaries is the expensive path: an access-control pass over every type the new consumer touches, and Bundle.main lookups that compile and then return nothing. A second app is a weekend at T3 from day one, a quarter retrofitted.

Ownership rules from T2 onward

  • Localization is per resource-owning module. Lookup resolves against a bundle, so each module with UI owns its .strings and a bundle-aware accessor — Bundle.module in a package, Bundle(for:) in a framework, never Bundle.main.
  • Theme is base plus per-app override, not one file.
  • Info.plist, entitlements, asset catalog, icon and signing are app-target-only.

Do's and don'ts

Once there's more than one module, every command has to resolve a destination before it can do anything. Most of the friction here is that question, asked repeatedly.

Do

Record a defaultModule once there's more than one candidate

Every command refuses to guess a destination without it, so you'll be answering "which module?" on each invocation until it's in the config. One line, answered once.

Do

Pass --ui when the module will own views

It's what wires in that module's localization and asset catalog at creation. Adding them to a module that was created without the flag is manual work the command won't redo for you.

Don't

Expect /add-module to work at T1

It refuses, with the reason: adding a module is the T1→T2 migration. Make that move deliberately rather than as a side effect of wanting one more folder.

Don't

Ask for a second app by copying the first

/add-app extends the shared base views and refuses to copy features across. A copied screen is two screens from the day it lands, and they diverge on the first bug fix.

05

Architecture

/new-feature Films "title:String,year:Int" on the MVVM default generates six files — flat feature folder, models hoisted to the shared package:

FileJobDoesn't know
FilmsViewRender state; loading, error and empty from DesignSystemWhere films come from
FilmsViewModel@Observable; owns state, depends on the repository protocolSwiftUI, or which host
FilmsRepositoryOwns the protocol's one real conformance; network or cacheThat a view exists
FilmsServiceBuilds the request, decodes the responseWhy it was wanted
Models/FilmsModelsRequest, Response, Entity — in the shared Models/Everything else
FilmsViewModelTestsFake conformance, no network, runs in millisecondsThe server

The protocol is owned by the consumer, not the implementer, and named for a capability (FilmsRepository) rather than a pattern (FilmsInteractorProtocol). No UseCase layer sits between ViewModel and Repository — a type that forwards one call is ceremony.

Four combinations are fully templated MVVM+SwiftUI, VIP+SwiftUI, VIP+UIKit and MVC+UIKit have every layer file written from a real template. Anything else — MVC+SwiftUI, MV, VIPER, or any pattern on its non-default navigation approach — still gets deterministic folders, models, DI wiring, navigation registration and a test scaffold, but the layer bodies are written by the assistant from your rendered architecture.md. If you didn't take the defaults, review before trusting.

Do's and don'ts

Six files arrive at once. Knowing which of them proves the other five are wired up is most of reviewing a generated feature.

Do

Run the generated test first

It ships passing, against a fake conformance, with no network — so it runs in milliseconds and it fails for exactly one reason: the wiring between the layers is wrong. Cheaper than reading six files.

Do

Treat a refusal on an existing folder as the guard working

/new-feature stops rather than merging into a half-built feature. Rename or remove first — talking it into proceeding is how you get two sets of layer files interleaved.

Don't

Let the pattern drift feature to feature

Nothing detects a feature built a different way — no hook, no lint rule, no check. Protocol and layer discipline is review here, and it's the failure that compounds most quietly.

Don't

Plan to move a feature into the right module afterwards

Generated into the wrong one, its models, DI registration, navigation entry and strings all land in the wrong place — and moving them is hand work. Answer the module question instead.

06

Day-to-day commands

Each already knows your recorded answers, so you never restate them.

Each declares its model in SKILL.md frontmatter, so the tier follows the work rather than whatever model your session is on. Four are pinned to opus at high effort — the ones that are irreversible or cross-cutting: /start, which writes the config every other command reads, plus the three that rewire feature, module or app wiring. The rest declare model: inherit and follow your /model choice, because a bounded, single-destination edit over an already-decided architecture has no business overriding it.

A pinned model replaces the session model for that run: /model sonnet then /status gives you Sonnet, but /model sonnet then /start still gives you Opus. That asymmetry is the point. There's no per-invocation flag — to change one anyway, edit the frontmatter in your project's own .claude/skills/<name>/SKILL.md.

Prose works, and gets confirmed first "Add a films list screen showing title and release year" reaches the same script — the agent translates it. Because that translation invents things prose can't carry, /new-feature batch-asks the three before generating: the field list with Swift types, whether the folder nests, and which module — then echoes the resolved command. Fully specified invocations skip the questions. The value of the command form is the checklist behind it: hoist the models, register the route, add strings to the owning module, generate a test that runs.

Do's and don'ts

Each command is a checklist with a script behind it. The failure modes are answering its questions badly, and doing by hand the part it was going to do in four places at once.

Do

Answer the three questions /new-feature batch-asks

Module, grouping, and the field list with Swift types. It never infers a type from an English noun, and a feature generated into the wrong module has to be moved by hand.

Do

Review what /translate writes

Draft entries for every existing key in the target locales, marked for review. Drafts, not shippable strings.

Don't

Hand-edit one of the files a command owns

/add-secret touches four places at once — the xcconfig, the committed example, each app's Info.plist and the typed accessor. Editing one by hand leaves the other three behind, and nothing tells you.

Don't

Paste a live API key, token or password into the chat

/add-secret writes an obvious placeholder for credential-shaped values and never echoes a held-back one — into TODO.md or anywhere else. The real value goes into the gitignored file by hand.

07

Xcode's own agents, and where this kit sits

Xcode now runs coding agents natively — Claude Agent and Codex, enabled under Xcode ▸ Settings ▸ Intelligence. Three consequences worth setting up deliberately.

Give terminal Claude Code access to Xcode's tools

Under Intelligence ▸ Model Context Protocol, turn on "Allow external agents to use Xcode tools", then register the bridge once:

Terminalone-time
claude mcp add --transport stdio xcode -- xcrun mcpbridge
claude mcp list   # verify

Keep the project open in Xcode; Xcode notifies you when an external agent connects and while it's active. The agent then builds and tests through Xcode itself rather than reconstructing xcodebuild invocations.

Permissions are global; project config isn't

  • Intelligence ▸ Agents ▸ Permissions holds the Allowed Commands and Allowed Tools lists. Anything you approved once in a transcript lands there and applies to every project on that Mac — worth auditing rather than accumulating.
  • Config under ~/Library/Developer/Xcode/CodingAssistant/ affects agents launched in Xcode only. Your repo's CLAUDE.md is read by both, and Xcode expects it beside the .xcodeproj — repo root at T1/T2, but not automatically at T3.
Use both, for different things Xcode's assistant is stronger where the editor is: inline fixes on a diagnostic, generated previews and playgrounds, doc comments, and its own built-in skills such as /plan. This template's scripts and core.hooksPath hooks are terminal-side regardless, so the terminal is the surface it's designed around. Whether the in-Xcode agent also picks up this repo's .claude/skills/ isn't something Apple documents — treat it as worth testing on your setup, not as given.

Do's and don'ts

Two agents on the same repo is fine. Two agents with different ideas about where the source of truth lives is not.

Do

Audit Intelligence ▸ Agents ▸ Permissions periodically

Anything you approved once in a transcript lands in Allowed Commands and applies to every project on that Mac — including repos you hadn't thought about when you approved it.

Do

Verify the bridge once, then watch for the notification

claude mcp add is a one-time registration — confirm it with claude mcp list. Xcode then tells you when an external agent connects and while it's active, which is how you know the terminal session is going through it.

Don't

Close the project once the bridge is registered

Keep it open in Xcode. That's what lets the agent build and test through Xcode itself rather than reconstructing an xcodebuild invocation.

Don't

Run both localization toolchains

Xcode's translation agent writes String Catalogs; /translate and the parity check operate on per-module .strings. Pick one — running both splits the source of truth, and the check won't see the half it doesn't own.

08

What's enforced

Two git hooks, wired via core.hooksPath, block four things:

CheckBlocks
hardcoded coloursUIColor(red:, Color(red:, (hex: and 6-digit hex literals in staged Swift outside any Theme/ directory
string key parityA key in the base locale missing from another, per module, plus cross-module duplicate keys
swiftlint --strictOne root config, every tier. try! errors; stray print( and raw Text("… inside a *View.swift warn
commit-msgAnything but PROJ-123 feat: summary — ticket prefix optional, type required from feat, fix, refactor, test, docs, chore. Merge commits exempt

Then tests, scoped to the staged change — at T3 only the affected schemes and their dependents, because a hook that runs every suite is a hook the team disables.

One guard is structural rather than a check: the .gitignore /start copies in already excludes Secrets.xcconfig, build products and xcuserdata/. A rule saying "don't commit secrets" against a repo that doesn't ignore them is worse than no rule, because the developer believes it.

The one deliberate deviation from stock convention Colours are never Asset Catalog colour sets. Every colour and font is a Swift value under Theme/: typed and compiler-checked from both SwiftUI and UIKit instead of string-keyed lookups that fail silently, mechanically enforceable by the colour check, and light/dark stays a one-file change. Across modules a token crosses as a public static let, where a catalog colour needs the right bundle at every lookup site.
09

Limitations

Deliberate scope calls and known gaps, not bugs. The two likeliest to reach you: off-default combinations are agent-written rather than templated, and localization and theming errors are runtime failures the compiler can't catch.

Four combinations are deterministic; the rest are assisted

And those four are T1/T2 shape — T3 placement is best-effort.

Two localization toolchains can collide

Xcode's translation agent writes String Catalogs (.xcstrings) and marks entries Machine Translated. /translate and check_strings.sh operate on per-module .strings. Pick one — running both splits the source of truth, and the parity check won't see the half it doesn't own.

No hardcoded-string check

A blanket regex false-positives on log messages, format strings and identifiers. The lint rule covers only Text("… in a view file, as a warning.

Bundle and theme correctness is unguarded

A framework reaching for Bundle.main compiles and returns nothing at runtime, in the consuming app only. Nothing stops app code redefining a token the shared module owns.

Protocol-boundary discipline is review, not tooling

Nothing detects a shared module that grew an app-specific branch, or a service protocol drifted to twenty methods.

/start's conflict handling is judgment

Idempotent, refuses structural changes as a re-run side effect, recreates what's missing — but it's reasoning about the tree, not a mechanical diff.

An offline project's data layer is one agent-written method

Answer None to networking and everything about a feature is still generated — folder, models, local store, composition-root factory, navigation registration, localization. What's left is the store read itself and its test, as TODO(agent), because the templated tests assert remote-vs-cache behaviour an offline feature doesn't have. Networking and persistence both None is refused with an explanation rather than scaffolded — there'd be no data layer at all.

Core Data's per-feature store is a seam, not an implementation

SwiftData is generated end to end — record type, store, schema registration, wiring. Core Data gets the same wiring but leaves its two store methods as TODO(agent), because the entity lives in a .xcdatamodeld that can't be generated from text. Until it exists, the app behaves like a no-persistence one.

No auth, deep linking or test tiers beyond unit

Nothing generates token refresh, Keychain storage or 401 retry; nothing maps an incoming URL onto a route; no UI or snapshot test target. Unaddressed so far rather than ruled out. The rule that credentials belong in the Keychain is documented; the wrapper implementing it is yours to write.

Deliberately out of scope

No CI pipeline, no pagination in the base repository contract, no image-caching library. Generated project files are committed, so a fresh clone opens without XcodeGen — at the cost of a pbxproj diff per regenerate.

The baseline is one codebase, not a survey

UIKit-heavy and hybrid. Games, offline-first or extension-heavy apps would calibrate differently.
