Skeleton — the guide

A starting kit for a new iOS app, set up so an AI coding assistant can work in it without having to re-learn your team's habits every time you talk to it. You answer eleven questions once. Out comes an app that already builds, a rulebook the assistant reads on its own, and a set of commands that add screens and settings the same way every time.

Written for everyone who will touch the project — iOS developers, backend or web developers moving across, QA engineers, and people shipping their first mobile app. iOS words are explained as they appear; hover any dashed word for a one-line definition, and see 00 for the full list. Each section opens with a In plain terms box: read those alone and you have the whole picture. You will need a Mac with Xcode installed. This guide covers starting from scratch — /start can also move an existing app onto this setup, but that isn't covered here.

00

Words you'll need

In plain terms

iOS has its own vocabulary, and most of it is just a name for something you already know from other kinds of software. This page is here so you can skim it once and then stop worrying about it. Nothing later depends on memorising this list — every term is also explained where it first comes up.

Apple's tools and files

Xcode
Apple's editor. It's where you write the code, press Run, and see the app. Free from the Mac App Store.
Simulator
A fake iPhone or iPad that runs on your Mac. You test in it before ever touching real hardware.
Swift
The programming language iOS apps are written in. Everything this kit generates is Swift.
.xcodeproj · .xcworkspace
The file you double-click to open the app in Xcode. A project is one app; a workspace groups several projects together.
pbxproj
The file inside a .xcodeproj that lists every source file. Notoriously painful to merge by hand, which is why this kit generates it instead.
Target
One thing that gets built. An app is a target; so is its test suite. One project can hold several.
Scheme
A saved "what to build and how" setting in Xcode — which target, debug or release. It's what the Run button obeys.
Bundle ID
Your app's unique name to Apple, written like a backwards web address: com.yourcompany.yourapp. Can't be changed casually once you've shipped.
Info.plist
A settings file baked into the app. Holds things iOS itself needs to read — the app's name, its version, and why it wants your camera.
.xcconfig
A plain text file of build settings, one KEY = value per line. This kit uses one to keep server addresses out of the code.
Asset Catalog
The folder Xcode keeps images and the app icon in. Named Assets.xcassets.
Entitlement · Capability
Permission granted by Apple rather than by the user — push notifications, iCloud, Sign in with Apple. Switched on in Xcode and in your Apple developer account.
Deployment target
The oldest iOS version your app will run on. Setting it higher lets you use newer Apple features but excludes older phones.
Keychain · UserDefaults
Two places to store small amounts of data. Keychain is encrypted and is where passwords and tokens belong; UserDefaults is not, and is for preferences like "dark mode on".

How the code is organised

SwiftUI · UIKit
The two ways to build screens. SwiftUI is the modern one — you describe what the screen looks like. UIKit is the older one — you build it piece by piece. Both are fully supported and both are still in wide use.
View
One screen, or a piece of one. Its only job is to display things.
Module · package · framework
A bundle of code kept separate from the rest, with its own boundary. Roughly what other ecosystems call a library. "Package" and "framework" are two ways iOS does this.
SPM (Swift Package Manager)
Apple's built-in tool for adding libraries and splitting your own code into packages. The equivalent of npm or pip.
Protocol
A list of what a type promises to do, without saying how. Called an interface in most other languages. It's what lets a test swap the real server for a fake one.
Architecture pattern
An agreed answer to "which file does what" — MVVM, VIP, MVC and so on. Its whole value is that everyone, including the assistant, picks the same answer.
ViewModel
The layer between the screen and the data. Holds what the screen currently shows, decides what to do when you tap. Knows nothing about how it looks.
Repository · Service
Where the data actually comes from. The service talks to the server; the repository decides whether to ask it or use what's already saved.
Dependency injection
Handing a piece of code the things it needs from outside, rather than letting it fetch them itself. It's what makes testing possible.
Composition root
The one place, at app launch, where all the real pieces get built and handed to each other. If wiring is wrong, it's wrong here.
Persistence
Saving data on the phone so it survives closing the app. SwiftData and Core Data are Apple's two options.
Localization
Keeping user-visible text in a separate file per language, rather than typed into the screen, so the app can be translated.
Bundle
The folder a built app or framework really is, containing its images and translations. Matters because looking in the wrong one gives you nothing — silently.
Theme token
A named colour or font — Theme.primary instead of "this exact shade of blue" typed in twenty places.
01

Why this exists

In plain terms

An AI assistant forgets everything between conversations. It can write a screen perfectly today and, tomorrow, write the next one a completely different way — files in a different place, data fetched by a different route. Neither one is wrong on its own; having both in the same app is the problem.

The fix is to write your decisions down in files the assistant reads automatically, every single time, before you say anything. That's most of what this kit is: those files, plus code that already follows them.

You might already know how to build the app. What's missing is a way to make an AI assistant build it the same way twice. It keeps no memory between sessions, so unless your conventions live somewhere it loads on its own, screen forty gets built however that morning's conversation happened to go — a different folder shape, a different way of moving between screens, a screen reaching out to the network directly instead of going through the layers below it.

This kit records those decisions once, during setup, into files the assistant reads at the start of every session — and it generates code that already follows them. It's a starting point and a rulebook. It is not a framework: nothing here is a library you import, and nothing takes over how your app runs.

What you get

  • An app that builds and runs on the first try — one working screen that already handles the three states every real screen needs (loading, failed, nothing to show), the code that talks to a server, named colours and fonts, translation files, and one test that already passes. The exception: if you tell setup your app has no server, one piece is deliberately left for you, and its test ships failing on purpose so you can't forget it.
  • Files the assistant loads by itself, so you never start a session by re-explaining the project — see 03.
  • Nine commands for the jobs you'll do over and over: add a screen, an image, a permission, a colour, a language, a module.
  • Automatic checks when you commit — colours typed in by hand, translations that have drifted out of sync, and style problems.
Read this before anything else This repository is the starting kit, not an app. There's no Xcode project in it, no chosen pattern, nothing app-shaped at all until you run /start. If you open the folder looking for an app to run, that's why you can't find one.

Where the recommended answers come from

Not opinion. They were taken from a real, long-lived codebase: the NIBE iOS project — two apps that ship to the App Store (one for customers, one for professionals) built on one shared core, roughly 20 screens each, 18 languages, seven years of history. We read the code and the record of how it changed, then wrote down what had actually held up over that time.

  • observedShared code supplies the parts; each app puts them together. The shared core holds the screens and the logic for moving between them; each app decides which to show and how. Wherever shared code instead asked "wait, am I the professional app?" and branched, that spot turned out to be the hardest to change later. So this kit keeps app-specific decisions inside the app.
  • observedEvery module with visible text needs all 18 languages, not just the app. When iOS looks up a piece of text, it looks inside whichever module owns that screen — not in the app. So each of those modules keeps its own complete set of translations. That's not a preference we chose; it's how the lookup works.
  • recommendedOnly write a protocol once you have a second thing that uses it. A fake version for tests counts as that second thing. A backend you might build one day does not.
02

Setup

In plain terms

Four things happen, once: install three small command-line tools, run /start, answer eleven questions, and paste your server address into one file. After that you have a real app you can open and run.

The eleven questions are the important part. Everything the kit generates afterwards is decided by your answers, and the commands you'll use for months keep reading them back. If you're not sure, say "use the recommended defaults" — that's a complete answer, not a cop-out.

Install the three command-line tools

These are the tools the kit's scripts call. Homebrew is the standard way to install command-line software on a Mac — think apt or Chocolatey.

Terminalone-time
# Homebrew itself, if you don't already have it — see brew.sh
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

brew install xcodegen jq swiftlint
  • xcodegen — writes the .xcodeproj (the file you open in Xcode) from a readable text file, project.yml. Install tuist instead if you pick Tuist below.
  • jq — reads JSON in the terminal. It's how every script looks up your answers in ios-skeleton.config.json. If it's missing, the scripts stop rather than guess.
  • swiftlint — checks Swift code style. Runs when you commit and when you build.

Run /start in Claude Code

Pick whichever of these two suits you — they end up in the same place.

Terminal — Claude Codepick one
# A: clone the kit and use it as the project, then run /start inside
git clone <template-repo-url> MyNewApp && cd MyNewApp
/start

# B: give it a folder name — it creates and fills the folder for you
/start MyNewApp

You don't copy any files yourself and you don't touch Xcode yet. Run this from the terminal — see 07 if you'd rather drive an assistant from inside Xcode.

Answer eleven questions

/start always shows you the whole list, whatever you said when you ran it. Say "use the recommended defaults" to accept them all in one reply — you'll still have seen every question. Your answers are checked together as a set — some combinations don't make sense — and then saved to ios-skeleton.config.json, which every command reads afterwards so you never have to repeat yourself.

The Why column below says what each question is really asking and what changes if you answer differently. You do not need to understand all of it to start; you do need to know that these answers are hard to change later.

Fill in Secrets.xcconfig before the first build

/start leaves two files at the top of the repo. Secrets.xcconfig.example is committed to git and records which settings exist. Secrets.xcconfig is ignored by git and holds the real values. Put your server address in API_BASE_URL there — never in the Swift code, so that a public repo can't leak it and each person can point at a different server.

Secrets.xcconfiggitignored
// `//` starts a comment in this file, so a URL's `//` needs the $() escape
API_BASE_URL = https:/$()/api.staging.example.com

From there the value travels into the app's Info.plist as a key called APIBaseURL. A single type in the shared core, AppEnvironment, reads it — that's the only place in the whole app that reads configuration — and hands it to RequestBuilder, which builds every outgoing request. Leave it empty and the app deliberately crashes at launch with a message naming the file to fix. That's on purpose: a quiet fallback address is how a test build ends up talking to the live server without anyone noticing. Every fresh clone of the repo needs this step again.

Why that $() is there

In this kind of file, // means "ignore the rest of the line". A URL has // in it. So https://host silently becomes just https: — the app then has a broken address and no error message. The $() sits between the two slashes so they're never next to each other while the file is being read, and disappears afterwards. Odd-looking, but it's a one-time copy-paste, and the check below catches you if you forget.

The launch check tests that the value has both a scheme and a host — not merely that some text was present — which is exactly what catches the mistake above. Quoting is not a way around it: this file format has no string literals and no escape character, so "https://host" gets truncated in exactly the same way. Scripts/check_secrets.sh applies the same rules when you commit, and docs/CODING_STANDARDS.md has the full explanation, including a table of what every form you might try resolves to.

If you answered None to the networking question, this step doesn't exist for you: an offline app gets no RequestBuilder, no APIBaseURL key and nothing to read it with, so there's nothing to fill in and nothing to crash about. The rule is don't generate the reader at all — never make the check lenient. Softening it to suit offline apps would trade a correct, loud crash for a networked app quietly pointing at the wrong server.

The Xcode project file is generated, so don't edit it Don't add, rename or move files in Xcode's file list on the left — the next time the project is regenerated, your change is gone. Edit project.yml instead, or use the commands in 06, which do it for you.

Do's and don'ts

Everything /start writes follows from your eleven answers, which makes that one conversation the one worth slowing down for.

Do

Answer the eleven together, as one set

They're checked as a set, not one at a time, because some combinations contradict each other. "Use the recommended defaults" is a complete, respectable answer. A guessed one spreads into every command that reads the config from then on.

Do

Re-run /start if something looks missing

It's safe to run twice: it recreates whatever is absent and refuses to quietly restructure what's already there. Reaching for it again is cheaper and safer than rebuilding a file by hand.

Don't

Copy the kit's files in by hand

/start walks them one file at a time and never overwrites anything already present — which is exactly what makes re-running it safe. A manual cp -r loses both of those properties.

Don't

Point /start at a hand-built Xcode project

It won't regenerate or overwrite one. Moving an existing codebase onto this setup is a different job from starting fresh, and it will say so rather than scaffolding over your work.

03

The rulebook

In plain terms

The assistant begins every conversation knowing nothing about your project. These files are the answers, written down in advance, so it doesn't have to guess or ask. One of them, CLAUDE.md, is read automatically before your first message and points at all the others.

The practical habit this asks of you is small: when you explain a constraint, put the sentence in a file rather than only in the chat. Chat is forgotten tomorrow; the file is read every time.

CLAUDE.md loads on its own and points at the rest. Together these files answer, up front, the questions the assistant would otherwise answer by guessing.

On a new project they arrive four ways

  • Copied in already finished — the rules that don't depend on your answers: colours and fonts, UI conventions, permissions, coding style, git habits.
  • Written out by /start — these ship describing every pattern and every project shape, and the setup step deletes the ones you didn't pick. So your docs describe one architecture, not five, and no half-filled placeholder survives.
  • Written by you — docs/product/. This kit knows how an app here is built and nothing whatsoever about what your app is for. Requirements arrive later and keep changing, so they're read fresh each time rather than summarised into CLAUDE.md.
  • Grown as you work — created at setup, then added to automatically by the commands that change what they describe.

Four Swift decisions the rulebook makes so nobody has to

If you're not a Swift developer, read this and skip the table

These four are long-running arguments in iOS development. None of them follow from your eleven answers, and an assistant left to itself will answer them by habit — differently each time. They're written down once, with the reasoning, so every generated file makes the same call.

You don't have to decide any of this. The value of the table is that the decision exists in writing and is anchored in code the kit actually ships — so if you ever need to know why something was done a particular way, the answer is on record instead of in someone's head.

QuestionThe call, and what it's anchored in
Where does this data go? UserDefaults for small, non-sensitive things like preferences · your chosen persistence stack for real records · Keychain for tokens and passwords, since it's the only encrypted store and the only one kept out of unencrypted backups. The hard line: never a credential in UserDefaults or the local database. And UserDefaults itself sits behind a small protocol rather than being reached for from anywhere as a global
GCD or async/await? async/await — and the generated code already is. Every service, repository and store is async throws, Debouncer is an actor, anything that owns UI is @MainActor, and no template contains a single DispatchQueue. GCD (the older approach) appears only where an outside SDK forces it, wrapped once at the boundary. An actor rather than a serial queue for shared mutable state; @MainActor rather than DispatchQueue.main.async; never a semaphore blocking on async work
When is [weak self] needed? Decided by which object owns which, not sprinkled everywhere out of caution. A closure stored on a long-lived object needs it — the generated retry handler is the example. A closure that's used and discarded doesn't, and adding it there is just noise. A reference pointing back up the ownership chain is always weak, which is why VIP's presenter holds its display layer weakly. Prefer weak over unowned: unowned crashes where weak quietly does nothing
struct or class? struct unless there's a reason. Use class for things with an identity (a coordinator, a view model), where a framework demands it (UIViewController, @Model, or anything that needs to be held weakly), or for @Observable view state. Models, RequestBuilder and the API client are structs because none of those apply. Mark classes final unless something subclasses them — and remember a struct holding a mutable reference is not really a value type
A stale doc is worse than a missing one A file describing a pattern you've since moved away from doesn't announce itself — it quietly steers the assistant wrong for months. That's why the commands update these files themselves instead of leaving it to memory, and why /status reports where what's written no longer matches what's actually on disk.

Do's and don'ts

These files exist so a session doesn't begin by re-establishing what the last one already knew. Using them well is mostly about where you put a sentence.

Do

Write the answer into a file, not just into the chat

The assistant has no memory between sessions. A constraint you explain in conversation is gone tomorrow. The same sentence in docs/product/ or PROJECT_MAP.md gets read every time, without you asking.

Do

Point at the file instead of pasting it in

"Read docs/product/api-contracts.md before building this service" costs a fraction of pasting the document — and it stays correct after someone edits the document.

Do

Let the commands do the writing-down

PROJECT_MAP.md, PERMISSIONS.md and TODO.md are created at setup and then updated by the commands that change what they describe. They grow as you work instead of depending on anyone remembering.

Don't

Re-explain your stack and pattern every session

CLAUDE.md is already loaded before your first message is read. Repeating it wastes room in the conversation — and a repetition that has drifted from the file is worse than saying nothing.

Don't

Summarise docs/product/ into CLAUDE.md

Requirements keep changing, and a summary goes stale without ever failing visibly. CLAUDE.md points at them and never summarises them; /new-feature re-reads the relevant one each time it runs.

Don't

Keep the patterns you didn't choose "for reference"

Setup deletes them deliberately, so your docs describe one architecture instead of five. A pattern left sitting in the file is a pattern the assistant may reasonably decide is still on the menu.

04

How the project is laid out

In plain terms

There are three sizes of project, called T1, T2 and T3. The layers of code are identical in all three — the only difference is how tightly they're separated, and therefore whether the compiler can stop somebody wiring two things together that shouldn't be.

T1 is one big bucket. T2 puts your shared code into separate packages, so crossing a boundary becomes a visible, deliberate act. T3 splits things further so two apps can share one core. T2 is the default, and the reason is timing: separating things now is a few minutes, separating them after a year is a project.

The layers are the same at all three sizes — only the packaging changes, which is what keeps moving between them manageable. What actually differs is whether the compiler can enforce a boundary or whether it's left to good intentions.

T1T2 defaultT3
Shapeone .xcodeproj, one app targetthe same, plus local Swift packages under Packages/an .xcworkspace over several projects: the app plus framework targets
Code boundariesone module — everything can see everythingone per package; using something from another package means marking it public on purposeone per framework, each buildable on its own
Files describing the buildone project.ymlplus a Package.swift per packageone per project, plus a generated workspace file
Where dependency versions are pinnedPackage.resolved, inside App.xcodeproj/…/swiftpm/moves to xcshareddata/swiftpm/
Good forprototypes, fewer than about 10 screensone app you intend to ship, any sizetwo apps sharing a core, or a framework you publish

Dependencies only ever point one direction — app → shared modules → the small building-block modules. Never a framework depending on the app, and never one app on another. When a shared module needs behaviour that differs per app, it takes that in as a protocol, handed to it at launch. /add-module refuses to create a loop, where two modules each need the other.

Cheap to add now, expensive to add later Adding a package or project is a text edit plus a regenerate — never hand-surgery on the Xcode project file. Pulling shared code out of an app that never had boundaries is the expensive path: you have to go through every type the new consumer touches and decide what becomes public, and untangle Bundle.main lookups that still compile happily and then return nothing at runtime. A second app is a weekend's work if you started at T3, and a quarter if you're retrofitting.

Who owns what, from T2 onward

  • Each module with UI owns its own translations. Text lookup happens inside whichever bundle owns the screen, so every module with visible text keeps its own text files and its own bundle-aware way of reading them — Bundle.module in a package, Bundle(for:) in a framework, and never Bundle.main.
  • Colours and fonts are a shared base plus a per-app override, not a single file everyone edits.
  • The Info.plist, entitlements, image catalog, app icon and signing belong to the app target only — never to a shared module.

Do's and don'ts

As soon as there's more than one module, every command has to work out where to put things before it can do anything. Most of the friction here is that one question, asked over and over.

Do

Record a defaultModule once there's more than one candidate

Commands refuse to guess a destination, so you'll be answering "which module?" every single time until it's saved in the config. One line, answered once.

Do

Pass --ui when the new module will contain screens

That flag is what sets up the module's translations and image catalog at the moment it's created. Adding them afterwards is manual work the command won't go back and do for you.

Don't

Expect /add-module to work at T1

It refuses and tells you why: adding a module is the move from T1 to T2. Better to make that decision deliberately than as a side effect of wanting one more folder.

Don't

Make a second app by copying the first

/add-app builds on the shared screens and refuses to copy features across. A copied screen is two screens from day one, and they start drifting apart at the first bug fix.

05

How a screen is built

In plain terms

One command produces a whole working screen as several small files, each with one job, none of them knowing more than it needs to. That last part is the point: the file that draws the screen doesn't know where the data came from, so you can swap in a fake one and test the screen with no server at all.

On the recommended answers, all of these files come from fixed templates — identical every time. On other combinations, some of them are written by the assistant instead, and that difference is worth knowing about before you review the result.

/new-feature Films "title:String,year:Int" on the default MVVM setup produces six files — a flat folder for the feature, with the data types lifted out into the shared package:

FileIts jobWhat it deliberately doesn't know
FilmsViewDraw the screen. Loading, error and empty states come ready-made from DesignSystemWhere the films came from
FilmsViewModelHold what's currently on screen and decide what happens on a tap. Depends on the repository protocol, not the real thingAnything about SwiftUI, or which screen shows it
FilmsRepositoryThe one real implementation of that protocol: decide whether to hit the network or use what's savedThat any screen exists
FilmsServiceBuild the network request and turn the response into Swift typesWhy anyone wanted it
Models/FilmsModelsThe data types — request, response, the thing itself — in the shared Models/Everything else
FilmsViewModelTestsTest the view model against a fake repository. No network, runs in millisecondsThe server

Two naming rules worth knowing, because they're the ones an assistant gets wrong by habit. The protocol belongs to the code that uses it, not the code that implements it. And it's named for what it does (FilmsRepository) rather than for the pattern it belongs to (FilmsInteractorProtocol). There's also no extra UseCase layer between the view model and the repository — a file whose only job is to pass one call along is ceremony.

Four combinations come from fixed templates MVVM+SwiftUI, VIP+SwiftUI, VIP+UIKit and MVC+UIKit have every layer file written from a real template — the same output every time, for everyone. Any other combination — MVC+SwiftUI, MV, VIPER, or any pattern paired with navigation other than its default — is assisted instead: you still get the folders, the data types, the wiring, the navigation entry and a test scaffold generated the same way every time, but the contents of the layer files are written by the assistant, guided by the architecture.md your setup produced.
If your combination isn't one of those four, expect to explain it Assisted does not mean automatic. Because the layer bodies depend on the mix of answers you gave — pattern, UI framework, navigation, persistence, DI — there is no single template that could cover them, so the assistant writes them from your written rules. In practice that means you should describe the pattern you want in your own words when you ask for a feature: what each layer is called, which layer may talk to which, where state lives, and what the first feature should look like when it's done. The clearer that description, the closer the result. Then read the generated files before building on them, and once you have one feature you're happy with, say so plainly — "match the structure of the Films feature" — so every later screen has a concrete example to copy rather than a description to interpret. If you'd rather not do any of this, take the recommended defaults; that's exactly what they're for.

Do's and don'ts

Six files land at once. Knowing which single one proves the other five are correctly connected is most of the skill in reviewing a generated feature.

Do

Run the generated test first

It ships passing, uses a fake data source, touches no network, and finishes in milliseconds — so it fails for essentially one reason: the layers aren't wired together properly. Far cheaper than reading six files.

Do

Treat a refusal on an existing folder as the guard doing its job

/new-feature stops rather than merging into a half-built feature. Rename or delete first. Talking it into continuing is how you end up with two sets of layer files tangled together.

Don't

Let the pattern drift from feature to feature

Nothing detects a feature built a different way — no hook, no lint rule, no check at all. Keeping to one shape is a review job, and it's the failure that builds up most quietly.

Don't

Plan to move a feature into the right module later

Generated into the wrong module, its data types, wiring, navigation entry and text all land in the wrong place too — and moving them is hand work. Answer the module question properly instead.

06

Day-to-day commands

In plain terms

These are the jobs you'll do repeatedly. Each one is a written checklist the assistant follows, plus scripts it runs — so adding an image or a permission touches every place it needs to, rather than the one place you remembered.

They already know your setup answers, so you never restate them. And you can describe what you want in ordinary English instead of typing the command; it reaches the same place.

Every command already knows your recorded answers, so you never have to repeat them.

Each one also declares which AI model it wants, in its own definition file — so the model follows the difficulty of the work instead of whatever your session happens to be set to. Four are pinned to Opus at high effort: the ones that are hard to undo or that touch many files at once — /start, which writes the config every other command reads, plus the three that rewire a feature, a module or an app. The rest say model: inherit and follow your /model choice, because a small, single-destination edit inside an architecture that's already decided has no business overriding what you picked.

A pinned model replaces your session model for that one run: /model sonnet then /status gives you Sonnet, but /model sonnet then /start still gives you Opus. That asymmetry is deliberate. There's no per-run flag to override it — to change one anyway, edit the header of your project's own .claude/skills/<name>/SKILL.md.

Do's and don'ts

Each command is a checklist with a script behind it. The two ways to get burned are answering its questions carelessly, and doing by hand the part it was about to do in four places at once.

Do

Answer the three questions /new-feature asks

Which module, whether the folder nests, and the fields with their Swift types. It will never guess a type from an English word, and a feature generated into the wrong module has to be moved by hand.

Do

Review what /translate writes

It drafts an entry for every existing piece of text in the languages you name, each marked as needing review. Drafts — not strings you can ship to users.

Don't

Hand-edit a file a command owns

/add-secret touches four places at once — the config file, the committed example, each app's Info.plist, and the typed accessor. Editing one by hand leaves the other three behind, and nothing will tell you.

Don't

Paste a real API key, token or password into the chat

/add-secret writes an obvious placeholder for anything credential-shaped, and never repeats a held-back value anywhere — not into TODO.md, not into the chat. The real value goes into the gitignored file by hand, by you.

07

Xcode's own assistants, and where this kit fits

In plain terms

Xcode now has AI assistants built in. They don't replace this kit and this kit doesn't replace them — they're good at different things. Xcode's is good at small fixes right where you're typing; this kit's commands and automatic checks live in the terminal.

Two things to set up deliberately: connect the terminal assistant to Xcode so it can build and run tests properly, and check what permissions you've handed out, because in Xcode those apply to every project on your Mac rather than just this one.

Xcode can now run coding assistants itself — Claude Agent and Codex — switched on under Xcode ▸ Settings ▸ Intelligence. Three consequences are worth handling on purpose rather than discovering later.

Let the terminal assistant use Xcode's own tools

Under Intelligence ▸ Model Context Protocol, turn on "Allow external agents to use Xcode tools", then register the connection once:

Terminalone-time
claude mcp add --transport stdio xcode -- xcrun mcpbridge
claude mcp list   # check it worked

Keep the project open in Xcode. Xcode tells you when an outside assistant connects and while it's working. With this in place, the assistant builds and runs tests through Xcode itself instead of trying to reconstruct the right xcodebuild command from scratch — which is where a lot of wasted time goes otherwise.

Permissions are Mac-wide; project settings aren't

  • Intelligence ▸ Agents ▸ Permissions holds the Allowed Commands and Allowed Tools lists. Anything you approved once, in any conversation, ends up there and then applies to every project on that Mac — worth reviewing occasionally rather than letting it pile up.
  • Settings under ~/Library/Developer/Xcode/CodingAssistant/ only affect assistants launched inside Xcode. Your repo's CLAUDE.md is read by both, and Xcode expects to find it next to the .xcodeproj — which is the repo root at T1 and T2, but not automatically at T3.
Use both, for different jobs Xcode's assistant is stronger wherever the editor is: fixing the error it's pointing at, generating previews and playgrounds, writing doc comments, and its own built-in commands like /plan. This kit's scripts and commit-time checks are terminal-side no matter what, so the terminal is the surface it's designed around. Whether the in-Xcode assistant also picks up this repo's .claude/skills/ isn't something Apple documents — treat that as worth testing on your own setup rather than assuming either way.

Do's and don'ts

Two assistants working on the same repo is fine. Two assistants with different ideas about where the truth lives is not.

Do

Review Intelligence ▸ Agents ▸ Permissions now and then

Anything approved once in a conversation lands in Allowed Commands and applies to every project on that Mac — including repos you weren't thinking about when you approved it.

Do

Check the connection once, then watch for the notification

claude mcp add is a one-time registration — confirm it with claude mcp list. After that Xcode tells you when an outside assistant connects and while it's active, which is how you know the terminal session is actually going through it.

Don't

Close the project once the connection is registered

Keep it open in Xcode. That's what lets the assistant build and test through Xcode rather than guessing at an xcodebuild command.

Don't

Run two translation systems at once

Xcode's translation assistant writes String Catalogs; /translate and the consistency check work on per-module .strings files. Pick one. Running both splits your text across two systems, and the check can't see the half it doesn't own.

08

What's checked for you

In plain terms

Some rules aren't left to memory or review — they run automatically when you commit, and stop the commit if something's wrong. Three things get blocked, and then the tests that relate to what you changed get run.

The reason to automate exactly these three is that they're the ones that fail quietly. A colour typed in by hand looks fine until dark mode; a missing translation looks fine until a user in that language opens the app.

One git hook — a set of checks that runs automatically at commit time — blocks three things:

CheckWhat it blocks
hardcoded coloursUIColor(red:, Color(red:, (hex: and six-digit hex values in any Swift file you're committing that isn't inside a Theme/ folder
translation consistencyText that exists in the main language but is missing from another, checked per module — plus the same key defined in two different modules
swiftlint --strictOne style config for the whole project, at every size. try! is an error; a stray print( or text typed straight into a *View.swift is a warning

Then the tests run, but only the ones related to what you changed — at T3, only the affected pieces and whatever depends on them. That's a deliberate choice: a commit check that runs every test in the project is a commit check the team eventually turns off.

One safeguard isn't a check at all but the way things are arranged: the .gitignore that /start puts in place already excludes Secrets.xcconfig, build output and personal Xcode settings. A written rule saying "don't commit secrets", in a repo that doesn't actually ignore them, is worse than no rule — because people believe it.

The one place this kit deliberately departs from the usual iOS convention Colours never go in the Asset Catalog. Normally you'd define a colour there and look it up by name. Here, every colour and font is a Swift value under Theme/. Four reasons: the compiler checks it, so a typo is a build error instead of an invisible fallback at runtime; it works identically from SwiftUI and UIKit; the colour check above can actually be enforced mechanically; and light/dark mode stays a change in one file. Across modules a colour crosses as an ordinary public static let, whereas an Asset Catalog colour needs the correct bundle at every single place it's used.
09

What it won't do

In plain terms

These are deliberate limits and known gaps, listed honestly — not bugs, and not a to-do list that's about to be finished. Read them before you plan around something that isn't here.

The two most likely to actually affect you: if you didn't take the recommended answers, some files are written by the assistant rather than from a template, so review them. And mistakes in translations or colours can't be caught by the compiler — they show up when the app is running, not when it's built.

Deliberate scope decisions and known gaps, not bugs. The two you're most likely to run into: if you went off the defaults, some layer files are assistant-written rather than templated; and translation and theming mistakes are runtime failures the compiler can't catch for you.

Four combinations are fully templated; everything else is assisted

And even those four are shaped for T1 and T2 — at T3, where files should go is a best guess. See 05 for what to do about it.

Two translation systems can collide

Xcode's translation assistant writes String Catalogs (.xcstrings) and marks entries as machine-translated. /translate and check_strings.sh work on per-module .strings files. Pick one — running both splits your text across two systems, and the consistency check can't see the half it doesn't own.

No check for text typed straight into a screen

A blanket search for quoted text flags far too much — log messages, format strings, internal identifiers. So the style rule only covers Text("… inside a view file, and only as a warning.

Bundle and theme correctness isn't guarded

A framework reaching for Bundle.main compiles perfectly and then finds nothing at runtime — and only inside the app using it. Nothing stops app code redefining a colour the shared module already owns.

Keeping to the layer boundaries is a review job, not a tool

Nothing detects a shared module that has grown an app-specific branch inside it, or a service protocol that has crept from three methods to twenty.

/start resolves conflicts by judgment, not by rule

It's safe to re-run, refuses to restructure things as a side effect, and recreates what's missing — but it's reasoning about your folder, not running a mechanical comparison.

An offline app's data layer is one method you or the assistant must write

Answer None to networking and almost everything about a feature is still generated — folder, data types, local store, wiring, navigation entry, translations. What's left is the actual read from local storage and its test, marked TODO(agent), because the templated tests check network-versus-cache behaviour that an offline feature simply doesn't have. Answering None to networking and persistence is refused with an explanation rather than scaffolded — there'd be no data layer left at all.

Core Data gets the wiring but not the implementation

SwiftData is generated end to end — record type, store, registration, wiring. Core Data gets the same wiring but leaves its two storage methods as TODO(agent), because a Core Data entity lives in a visual model file that can't be generated from text. Until someone creates it, the app behaves as if it had no persistence at all.

No login, deep links, or tests beyond unit tests

Nothing generates token refresh, Keychain storage or retry-after-401; nothing turns an incoming link into a screen; there's no UI or screenshot test target. Not ruled out — just not done yet. The rule that credentials belong in the Keychain is written down; the code implementing it is yours to write.

Deliberately left out

No commit-message enforcement. docs/GIT_CONVENTIONS.md suggests a format, but nothing checks it — commit conventions differ from team to team and from client to client, so that's your project's call to make, not this kit's. Add your own commit-msg hook if you want it enforced. Also no CI pipeline, no paging in the base data contract, and no image-caching library. Generated project files are committed, so a fresh clone opens in Xcode without needing XcodeGen installed — at the cost of a noisy project-file diff each time it's regenerated.

The recommendations come from one codebase, not a survey

And a UIKit-heavy, partly-hybrid one. A game, an offline-first app or something built mostly of extensions would reasonably land on different answers.
